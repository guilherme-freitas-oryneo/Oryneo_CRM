# ORYNEO User Permissions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Tornar a conta atual administradora e aplicar isolamento de oportunidades, papéis e restrição de campos sensíveis no banco e na interface.

**Architecture:** Papéis e estado residem em `crm_members`; UUID da sessão vem de Supabase Auth. O proprietário da oportunidade fica em coluna tipada. RLS limita linhas; uma API de leitura controlada projeta apenas campos permitidos, porque o JSONB atual mistura dados comerciais e de contato. RPCs/Edge Functions verificam as mesmas capacidades antes de gravar.

**Tech Stack:** PostgreSQL 17/RLS, Supabase Auth/Edge Functions, React 19/TypeScript, QA SQL local com PostgreSQL Docker e QA Playwright existente.

**Spec:** `docs/superpowers/specs/2026-10-11-rbac-design.md`

## Global Constraints

- A conta única vinculada a `guilherme.freitas@oryneo.com.br` é a administradora inicial; abortar bootstrap se o match não for único.
- Oportunidades já existentes e recebidas da LP ficam sem responsável até atribuição administrativa; não inventar proprietário.
- Perfis `support` e `viewer` não recebem valor, proposta ou eventos financeiros.
- `service_role` e Auth Admin API ficam no backend; nenhum token privilegiado no frontend.
- Fazer deploy backend antes do frontend; não ativar política nova antes de cliente e testes compatíveis.

## Review Focus

- UUID de oportunidade conhecida de outro usuário: REST, RPC e Edge Function devem negar o acesso.
- Usuário suspenso ou papel alterado com JWT antigo: próxima consulta deve obedecer ao banco.
- Reatribuição ou revogação entre leitura e escrita: mutação deve falhar dentro da transação.
- JSONB e histórico/eventos: ausência de valor/proposta em respostas a suporte/leitura.
- Bootstrap e último admin: abortar diante de identidade ambígua ou tentativa de remover o último admin.
